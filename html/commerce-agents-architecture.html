Commerce Agents 系统架构

两个基于 Claude 的电商 Agent——购物助手和商家助手——的完整参考实现。一套提示词、技能和工具合约，定义一次，在 Messages API、Agent SDK 和 Managed Agents 三条路径上运行；四个行业示例展示从目录搜索到库存管理的完整流程。

一轮对话里发生了什么

以购物场景为例：用户输入 "一顶两人帐篷，250 美元以内"，Messages API 路径下的完整处理流程如下。

1

预取上下文 — 并行调用 get_preferences、get_cart、tier_one 记忆事实和 get_account_context。结果放入缓存断点之后的围栏块（fenced block），模型读取但不能作为指令执行。

2

接地检查（Grounding） — first_forced_tool() 将用户消息与词表匹配：如果是退货/政策问题，强制先调用 search_policies；如果提及未见过的产品 ID，强制 get_product_details。本例不触发任何规则，模型自由选择工具。

3

模型调用 search_products — 参数 query="two-person tent", filters={max_price: 250}。执行器将 limit 钳制到 max_search_results，调用 StorefrontBackend.search_products，结果经 Fence.fence_payload() 消毒和围栏后返回。匹配的产品 ID 记入会话的 seen_products 来源追踪表（LRU，上限 200）。

4

模型调用 present_products — 参数 product_ids=["T-01", "T-02", "T-03"]。run_presentation() 验证 payload schema，调用 enrich_products() 从 seen_products 解析每个 ID 的完整记录，丢弃无来源的 ID，生成 ui 事件。流式传输时先产生 ui_partial 事件，让前端逐步渲染。

5

模型调用 present_suggestions — 参数 suggestions=["看帐篷详情", "比较前两顶", "加入购物车"]。建议芯片经 sanitize_suggestion_chips() 消毒（上限 4 条），产生 ui 事件。

6

回合结束 — 这一轮包含建议芯片且所有展示调用均成功（close_on_presentation），回合关闭。运行时产生 turn_complete 事件（含 usage、elapsed_ms）。之后 update_memory() 用记忆模型（默认 claude-haiku-4-5）从对话文本提取事实存入记忆。

上述六步发生在一次 HTTP 请求内，通过 SSE（Server-Sent Events）流式推送 text_delta、tool_call、tool_result、ui、turn_complete 等十种事件类型。EagerDispatcher 在流式响应中一个工具块关闭时立即开始执行，与模型生成重叠。

两个 Agent

项目定义了两个角色：面向顾客的购物 Agent和面向运营人员的商家 Agent。每个角色有一套提示词、五个技能、一组工具合约和一个后端接口。

Shopping Agent

购物 Agent

用途：嵌入商家 App，帮助顾客搜索、比较、规划、下单、查看订单和政策。

默认模型：claude-sonnet-5

后端接口：StorefrontBackend（shopping_agent/backend.py）——目录搜索、商品详情、购物车读写、用户偏好、订单、政策、配送、披露信息。购物车操作是唯一的写入；checkout 不下单也不收费，只渲染购物车交给宿主完成。

20+ 工具，包括目录工具、购物车工具、订单工具、记忆工具和展示工具。

五个技能
  • search-discovery 将描述的需求变成候选清单和推荐
  • planning-goals 为目标、活动或旅行规划一组协调的采购
  • purchase-research 在候选出现之前教顾客如何选择
  • memory-personalization 记住、回忆、修正、遗忘顾客偏好
  • customer-care 售后服务：订单状态、退换货、店铺政策
安全门控

来源追踪门（gates.py）：购物车写入只接受本会话中目录或订单工具返回过的产品 ID。选项门：对有选项的家族产品（如 S/M/L）拒绝直接添加，要求指定变体。单品数量上限 24，购物车行数上限 100，同一会话的购物车写入串行化。

Merchant Agent

商家 Agent

用途：供运营人员使用的后台助手，解释业绩、维护商品、处理库存和订单警报、定价促销、草拟营销活动。所有写入都是暂存提案，需人工批准后才生效。

默认模型：claude-opus-5

后端接口：MerchantBackend（merchant_agent/backend.py）——业绩快照、指标查询、活动绩效、商品目录、库存警报、订单异常、定价上下文、五种暂存写入（stage_*）、待审变更列表、应用/丢弃变更、分析查询。只有 apply_change 修改线上状态。

分析委托：独立的模型调用（delegation.py），接收简报和只读工具，返回 schema 验证的 AnalysisResult。SQL 查询仅允许 SELECT，行数和字符数有上限，有超时和调用次数限制。仅 Messages API 路径完整支持。

五个技能
  • performance-insights 指标为什么变动、细分归因、对标分析
  • catalog-listings 商品内容创建、质量审计、属性补全
  • inventory-operations 库存监控、警报分拣、每日简报
  • pricing-promotions 在护栏内调价、促销、折扣建议
  • marketing-campaigns 活动草拟、受众选择、预算分配
暂存→批准→应用

写入流程：stage_* 方法创建提案 → 护栏检查（changes.py：单次最多 25 项，价格幅度 ≤20%，促销深度 ≤50%，补货 ≤500，活动预算 ≤10000）→ 宿主审批界面标记通过 → apply_change 执行平台写入并再次检查护栏。require_host_approval 默认开启。

分层架构

整个系统分为四层。上层依赖下层；同层之间不互相依赖。

每一层的代码都是独立的 pip 包。共享层定义一次、两个核心各自扩展、三条运行路径各自集成、行业示例各自实现后端和 UI。一个机制只在一处定义。

共享基础设施：commerce_common

两个角色共享的全部机制。每个模块处理一个关注点，在 commerce-common/commerce_common/ 下。

skillsSkillRegistry：加载 SKILL.md 目录，渲染索引，按需返回

presentationPresentationComponent、PresentationExtension、验证和服务端填充

三条运行路径

同一个 Agent（相同的提示词、技能和工具合约）在三种不同的运行架构上运行。区别在于谁驱动循环和哪些运行时功能可用。

维度 Messages API Agent SDK Managed Agents
谁驱动循环 宿主应用（orchestrator.py） SDK（ClaudeAgentOptions） 平台
入口类 ShoppingAgent / MerchantAgent make_options() + Toolset agent.yaml + MCP server
接地规则 完整（全部规则，通过 tool_choice 强制） 预取形式（有 prefetch_intro 的规则） 无
记忆提取 回合后自动（update_memory()） 宿主调用运行时 仅通过 save_memory 工具
急切工具分发 支持（EagerDispatcher，重叠工具执行与生成） 不支持 不支持
历史压缩 支持（超过 compact_history_above_tokens 时清除旧结果） SDK 管理 平台管理
流式部分 UI 支持（ui_partial 事件） 不支持 不支持
分析委托 完整（独立调用，SQL 查询，预算限制） 子 Agent（只读工具，无 SQL，无预算） 不支持
技能加载 load_skill 工具 SDK 的 Skill 工具（适配器） Skills API（平台上传）
状态行 支持（工具调用时的进度提示） 不支持 不支持
商家审批 门户的审批路由 控制台 y/N 平台的 always_ask

所有路径共享同一个执行器（commerce_common/execution.py + 各角色的 executor.py），因此工具调用内的安全规则（围栏、来源追踪、数量上限、护栏）在三条路径上一致。

安全机制

安全规则分三层：代码强制（在工具调用内执行，三条路径一致）、提示词要求（模型遵循指令）、部署方负责（认证、凭证、业务规则等）。以下列出代码强制的核心规则。

规则 实现位置 作用
围栏（Fencing） commerce_common/fencing.py 第三方文本消毒（移除不可见字符、伪造标记、围栏标签副本），固定标签围栏包裹，字符数上限 max_fenced_chars（默认 12,000）
来源追踪 shopping_agent/gates.py、merchant_agent/gates.py 购物车和暂存写入只接受本会话中工具返回过的 ID；内容编辑还需要先 get_listing；应用/丢弃只接受返回过的 change ID
数量和价格上限 shopping_agent/config.py、merchant_agent/changes.py 购物车：单品 24、行数 100。商家护栏：单次 25 项、价格 ±20%、促销 ≤50%、补货 ≤500、预算 ≤10,000
无支付 StorefrontBackend（无下单方法） checkout 渲染购物车交给宿主；托管结账 URL 由 checkout_handoff 在模型调用之后注入，模型不可见
宿主审批 merchant_agent/gates.py apply_change 仅对宿主标记为 approved 的变更放行。默认开启。
UI 验证 commerce_common/presentation.py 展示调用经 schema 验证，然后服务端从会话记录填充每个产品/指标/变更的实际数据；无来源的 ID 被丢弃
记忆写入过滤 commerce_common/memory.py 键 ≤64 字符、值 ≤200 字符、三种类别之一。默认阻止标识符形状的值（9+ 位数字、IBAN、邮箱）
分析 SQL 检查 merchant_agent/analysis.py 仅允许 SELECT，无注释，禁止关键字正则。结果行数和字符数有上限，有超时
身份隔离 examples/demo_common/sessions.py 会话绑定主体到不可猜测的 session ID；后续请求只携带该 ID；模型不接触凭证
MCP 绑定 commerce_common/mcp_server.py MCP server 拒绝非回环绑定，除非声明了认证网关

提示词层另外要求：围栏文本是待报告的材料而非指令；术语和数字只从工具结果引用；写入在调用成功后确认；专业/医疗/安全问题给出产品和转介。当模型违反提示词规则时，错误仅限于其文本——背后的写入、数字和披露信息仍通过了代码检查。

部署方负责认证和授权、凭证管理、速率限制、业务规则、支付、记忆作为个人数据的处理（保留期、查看和删除）、日志卫生、审批界面和护栏值的配置。详见 docs/safety.md。

快速启动

git clone https://github.com/anthropics/commerce-agents.git && cd commerce-agents
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt       # 七个包及其固定依赖
cp .env.example .env                  # 添加 ANTHROPIC_API_KEY
(cd examples && npm ci)               # 八个 Web 应用共享一个 npm workspace
python scripts/run_demo.py retail     # API :8000 + 店面 :3000

--merchant 启动门户而非店面，--all 同时启动两者。验证命令：

ruff check . && ruff format --check . && pytest && python scripts/check.py
python scripts/verify_all.py          # 上面的命令 + 部署模拟和 Web 构建
