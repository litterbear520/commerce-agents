一个模型，两位店员，三条路径

这是 commerce-agents 仓库的架构说明：一个面向顾客的购物助理、一个面向店员的商家助理，各自只定义一次（提示词、技能、工具契约、安全门），共用同一套底层机制，跑在 Messages API、Claude Agent SDK 和 Managed Agents 三条路径上。图解依据官方文章 The anatomy of effective commerce agents 与仓库源码整理。

01

一个模型，一个标准循环

没有意图路由，没有按领域拆的子代理。一个 Claude 在标准的 agent loop 里对话，环境里放着工具、技能、界面组件和记忆。

官方文章的核心结论：单个代理 + 技能在质量、成本和延迟上都胜过子代理架构。商业对话往往一句话里有多个意图（"帐篷要 250 以内，顺便看看上次订单到哪了"），拆成子代理就得来回交接上下文，付"交接税"。所以这个仓库里两个角色都只有一个模型在说话；技能通过 load_skill 作为工具结果读入，界面组件是带类型的工具调用，记忆是数据库里的小型事实记录。

模型只负责选择和标注；跑循环、执行工具、校验参数、补全数据、执行审批、向客户端流式输出，都是宿主（harness）的事。这条分界贯穿整页。

放系统提示词还是放技能？按频率。三分之一以上的流量都需要的规则（商品搜索、购物车语义、展示规则、事实来源）进系统提示词；其余进技能。两边各五个技能，每个是 skills/<flow>/SKILL.md。
02

两个角色，一套骨架

店门口一个，柜台后面一个。各自有核心包、五个技能和自己的后端接口；共用的机制只在 commerce_common 里定义一次。

  • 购物助理：搜索、比较、凑方案、填购物车、答订单和政策问题、记住顾客说过的话。checkout 只渲染购物车与结账交接卡，后端接口里根本没有扣款方法。
  • 商家助理：解释业绩、维护商品页、处理库存与订单告警、调价促销、起草营销稿。每次写入先进账本成为暂存变更，宿主的审批界面点了才应用。
  • 模型选择：文章建议消费者侧从 Sonnet 起步（对延迟敏感），商家侧从 Opus 起步（分析重）；仓库默认值正是如此，可在各自 config.py 改。
03

分层：从界面到你的系统

上层调用下层，下层不知道上层。核心与共享层不依赖任何运行路径，所以同一份代码能跑在三条路径上。

04

一句话进来，发生了什么

以 Messages API 路径为例：从客户端 POST 到 turn_complete，一个回合里五方各做什么、什么时候把字节流回浏览器。

  • grounding（grounding.py）：某些消息形状要先读再答。顾客问条款、问已购订单、提到没见过的商品 id；店员问业绩、或没有暂存就要求"应用"。Messages API 路径用 tool_choice 强制第一轮调对应的读工具。
  • 渐进渲染：对展示工具打开 eager_input_streaming，参数边生成边解析（parse_partial_json），卡片的第一项在第一个键到达时就以 ui_partial 出现。
  • 历史压缩：超过 compact_history_above_tokens 后，运行时清掉存储对话里最旧的工具结果。
05

请求怎样分段，缓存才命中

缓存读取的价格是新 token 的十分之一。把请求按"变化频率"排序：最稳的放最前面，每回合才变的放最后面。

这是成本和延迟的头号杠杆，高流量部署的命中率通常在 90% 到 99%。规则只有一条：断点之前的字节一个都不能变。prompt_assembly.py 把断点放在三处：静态系统文本之后、工具数组最后一个之后、对话里最新持久化的消息上（每回合向前滚动）。所有每请求才变的数据（购物车、当前页面、时钟、记忆事实）放进第二个 system 块，位于断点之后。

06

UI 组件就是工具

模型不写标记语言，也不背价格。它调一个带类型的展示工具，只给出 id 和标注；服务端校验、联表补全，再以 ui 事件流给客户端。

内置组件在各角色的 tools/presentation.py：购物侧有商品卡组、比较表、方案、指南、订单状态、披露框、建议 chips；商家侧有摘要、指标、变更预览、建议 chips。垂类通过 PresentationExtension 加自己的：行程单、入住日历、套餐矩阵、场馆图、事件节奏，共七个。

07

Claude 说了不算，门口有人查

安全规则不靠提示词"请不要"，而在宿主里执行：模型提议，代码或人来放行。规则写在工具调用里，所以三条路径同样有效。

先看购物侧。写购物车只接受本会话里工具返回过的商品 id（或已在购物车里的行）；模型凭空编一个 id，门会把调用挡住，返回一个 status: blocked 的正常结果并指回搜索。上限在写入后的状态上检查，不在请求上；同一会话的购物车写入串行。

商家侧多一层。每个写工具都是 stage_*：先过护栏，进入账本成为一条暂存变更，拿到服务端生成的 change_id，以预览卡展示给店员。apply_change 只对宿主标记为已批准的 id 成功，并在应用时按当时生效的上限再跑一次护栏。预览卡不批准任何东西，聊天里打一句"同意"也不算。

围栏 fencing

第三方文本（商品页、评论、政策）先消毒：去掉零宽/控制字符、伪造的轮次标记、转录和工具调用标签、围栏标记的复制品；再包进固定标签的围栏，截到 max_fenced_chars。每请求上下文块也在围栏里。

披露文本服务端出

受监管的费用、条款由 get_disclosure 逐字提供；模型只选"给哪个商品"。评估里按字节比对。

记忆写入过滤

事实：key ≤ 64 字、value ≤ 200 字、三类之一；像标识符的值默认拒绝。抽取只读用户与助手的文本，从不读工具结果。

工具面由配置决定

工具列表是部署配置的函数；执行器拒绝其他名字。SDK 路径把同一份名字放进 allow-list；Managed Agents 清单逐个启用。

09

接到你的系统上

核心是领域中性的。一个部署要做的事只有四件：实现后端接口、关掉没有的系统、加自己的界面组件、设品牌身份。

1 · 实现后端接口

继承 StorefrontBackend 或 MerchantBackend，每个方法在服务端用宿主持有的凭证调你的服务，模型只读结果。先做搜索和商品详情，其余先 stub：返回"不可用"，不改任何提示词字节。

2 · 关掉没有的系统

enable_cart、enable_orders、enable_policies、enable_fulfillment；商家侧 enable_listing_edits、enable_inventory、enable_pricing、enable_campaigns。关一个开关，同时移除工具、提示词行和 grounding 规则。

3 · 加领域界面

一个 PresentationExtension = 一个工具名 + payload schema + 补全函数 + 组件名。走同一个运行器，同样的校验和来源检查。

4 · 设身份与技能

brand_name、assistant_name、brand_voice；新流程就是 skills/ 下一个带 SKILL.md 的目录，暂时不用的放 skills/_staged/。

四个可运行的垂类展示"同一套库上长出不同的店"。它们只在最上层（Next.js 界面、扩展组件）和最下层（mock 数据）出现：

10

仓库地图与阅读顺序

七个 pip 包从各自目录安装（requirements.txt），八个 Web 应用共用一个 npm workspace（examples/）。

commerce-agents/
├── commerce-common/commerce_common/     # 共享层：fencing · memory · skills · prompt_assembly
│                                        #         grounding · presentation · execution · streaming · turn
├── shopping-agent/
│   ├── core/shopping_agent/             # types · backend · prompt · tools/ · gates · enrichment · executor
│   ├── skills/                          # 5 个 SKILL.md
│   ├── runtime-messages-api/            # ShoppingAgent（orchestrator.py）
│   ├── runtime-agent-sdk/               # ClaudeAgentOptions + 控制台
│   └── managed-agents/                  # agent.yaml · system.md · storefront MCP server
├── merchant-agent/                      # 同上结构，多 changes.py（账本/护栏）与 analysis.py（分析代理）
├── examples/
│   ├── demo_common/  web-shared/        # 垂类共用的 FastAPI 宿主与 React 组件
│   └── retail/ travel/ telecom/ entertainment/   # api/ · data/ · storefront-web/ · merchant-web/
├── plugins/commerce-builder/            # 6 个技能 · 4 个命令
├── docs/                                # safety.md · backends.md · deployment.md
├── scripts/                             # install · run_demo · smoke_chat · check · deploy · verify_all
└── tests/                               # 跨包套件：两个角色 × 三条路径

想按机制读源码，建议这个顺序，每一步只看一个文件的顶部注释和公开函数：

  1. 循环怎么跑 · shopping-agent/runtime-messages-api/shopping_agent_runtime/orchestrator.py 的 stream_turn：轮次、tool_choice、断点、事件。
  2. 请求怎么拼 · commerce-common/commerce_common/prompt_assembly.py；再看 shopping_agent/prompt.py 的 build_dynamic_context。
  3. 工具结果怎么造 · commerce_common/execution.py 的 execute / dispatch，以及 shopping_agent/executor.py。
  4. 门怎么挡 · shopping_agent/gates.py、merchant_agent/gates.py、merchant_agent/changes.py；对照 docs/safety.md 的表。
  5. UI 怎么补全 · commerce_common/presentation.py 的 run_presentation，再看一个垂类的 PresentationExtension（如 examples/travel/api/）。
  6. 另两条路径 · commerce_common/agent_sdk.py 的 make_options；managed-agents/*/agent.yaml 与 commerce_common/manifest.py。
  7. 验证一致性 · scripts/check.py 比对派生的 system.md；tests/ 里的跨路径套件。
