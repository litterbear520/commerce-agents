# 后端：映射你的系统

`StorefrontBackend` 和 `MerchantBackend` 将你的系统转换为代理读取的记录。本指南涵盖身份与凭证、有序流程、结账、带选项的产品以及缺失数据。每个角色的 `backend.py` 和 `types.py` 中的方法文档字符串即为接口契约。零售和电信示例展示了完整运行。

## 第 1 步：确定调用者身份及认证方式

**在会话开始时绑定身份。**  你的宿主认证调用者并使用其解析出的主体启动会话：购物代理使用客户 id，商户代理使用商户 id 和操作员。每个后端方法都接收该会话对象并从中读取身份。任何路由和工具参数都不传递用户 id。

**将凭证与身份放在一起。**  后端为该主体调用你的平台所需的一切都存放在会话中，而不是模型中：

- 每客户令牌：放在会话上下文的子类中，或放在你的宿主在登录时填充、后端按客户 id 读取的存储中。
- 服务凭证：通过后端的构造函数传入。

**将访客视为主体。**  将会话标记为访客。当读取操作需要账户（订单历史、保存的地址）时，抛出异常，由你的 executor 子类将其转化为"请客户登录"。当访客登录后，启动新会话。示例宿主在会话开始时接受一个演示用户 id，作为真实登录的替代。

**在 Managed Agents 上，**  平台在保管库中为每个 MCP 服务器持有一个凭证，你的 MCP 服务器从经过认证的请求中获取客户身份。可以通过为每个客户会话使用一个保管库凭证来传递每客户身份，也可以使用你的网关在每次请求中验证的签名声明。

## 第 2 步：保持多步骤流程的顺序

有些流程只有按顺序执行才有意义：验证身份、检查资格、然后提交；保留座位、然后确认。后端负责强制执行该顺序。

1. 在后端中保持流程状态，以会话为键。
2. 当一个调用在其依赖步骤之前到达时，抛出你自己的异常类。
3. 在 executor 子类中映射该异常类（`domain_error`），使工具结果说明缺失的步骤，而不是看起来像系统故障。模型随后会告知客户应先完成什么。
4. 对于你的平台会去重的写操作，从会话 id 和购物车行的哈希值派生幂等键。
5. 当客户在对话外完成某个步骤（支付页面、验证码）时，由宿主在会话上排入应用事件；下一轮对话读取它。

娱乐示例的票务引擎以这种方式强制执行保留限制、过期和所有权，其 executor 子类将引擎的消息中继给模型。

## 第 3 步：确定结账如何完成

`checkout` 工具结束代理的部分：它渲染购物车。本仓库中没有任何代码下单或收款。为结账卡片选择以下三种交接方式之一：

| 你的场景 | 卡片行为 | 你需要实现的 |
|---|---|---|
| 结账是你应用中的一个路由 | 链接到该路由 | 无需实现；使用默认行为 |
| 平台托管结账（购物车 API 无法在服务端收款） | 打开平台的托管结账 URL | `checkout_handoff` 返回该购物车的 URL |
| 每个卖家单独结账的市场平台 | 每个卖家显示一个链接 | `checkout_handoff` 返回每个卖家一个条目 |

executor 在模型调用之后将 `checkout_handoff` 的返回值添加到卡片的 payload 中，因此 URL 不会经过模型。示例卡片仅链接 `https` URL。当支付完成时，排入应用事件以便下一轮对话知晓。

## 第 4 步：映射带选项的产品

产品或商品记录有三种形态：

| 形态 | 如何识别 | 代理如何处理 |
|---|---|---|
| 简单产品 | 没有选项 | 搜索返回它；购物车、价格更新和补货使用其 id |
| 产品族 | 有 `options`，如 size: twin, queen, king | 搜索返回它；详情列出其变体。购物车、价格和补货写入需要变体 id；暂停、促销和内容编辑可以使用产品族名称 |
| 变体 | 有 `option_values`（每个选项一个值）和 `variant_of`（产品族的 id） | 在其产品族的详情中返回，拥有自己的 id、价格和库存；购物车、价格更新和补货使用其 id |

变体的 id 用在所有需要产品或商品 id 的地方；不存在单独的变体 id 字段。产品族和变体的 id 共享一个命名空间，因此如果父级的平台 id 可能与子级相同，请在后端中为产品族 id 添加前缀。搜索会匹配选项值和属性，因此像 size = king 这样的过滤条件可以生效。如果后端已经从查询中解析出了所有选项，可以在搜索中直接返回变体；否则搜索返回产品族。

**从常见目录模型映射。**

| 你的目录 | 产品族 | 变体 | 简单产品 |
|---|---|---|---|
| 父子记录；父级不可购买 | 父级：其 id、内容和变体属性作为选项 | 每个子级：id、价格、库存、选项值、父级 id | 独立产品 |
| 每行都是可购买的 SKU；同组共享一个组键（购物数据源） | 合成的：以带前缀的组键为 id，第一行的标题和图片，从各行收集的选项；详情解析该 id | 每行，以合成的 id 作为其产品族 | 没有组的行 |
| 产品外壳始终有变体；价格和库存仅在变体上 | 产品：id、内容、选项名称和值 | 每个变体 | 单变体产品，以变体的 id 提供，不带选项 |

```text
your platform                              this record
product  P-88  "Trail Tee"                 {"product_id": "P-88", "title": "Trail Tee", "price": 24.0,
  option  size: S M L                       "options": {"size": ["S", "M", "L"]}}
  variant V-1  S  24.00  12 in stock       details.variants[0] = {"product_id": "V-1", "price": 24.0,
  variant V-2  M  24.00   0 in stock         "in_stock": true, "option_values": {"size": "S"},
  variant V-3  L  26.00   4 in stock         "variant_of": "P-88"}  … and V-2, V-3
```

**什么不是变体。**

- 按请求计算的价格或可用性（搜索日期的每晚价格、按人数计算的费用、座位）。请求的维度作为搜索过滤条件传入，返回的记录是该上下文的报价。旅行示例的价格就是这种方式。房间类型独立定价和管理库存的预订引擎仍可将其列为物业的变体。
- 不仅在选项值上不同的同类产品（具有各自分区和费用的票务等级；具有各自配额的套餐等级）。将它们作为按属性分组的独立记录，如娱乐示例所示。
- 一个产品由多个卖家以不同价格销售。一条记录只有一个价格：返回你要售出的报价，或将每个报价作为单独的记录列出。
- 定制产品、捆绑包和带修改项的菜单项。选项作为请求属性或在你自己的购物车扩展中传递，由后端定价。
- 按称重计价的商品。数量按整数计，因此以固定包装销售，这些包装本身可以是变体。

**产品族自身的数据。**

- 店面价格是库存中最低变体的价格（"起"价）；只要任何变体有库存，产品族就是有库存的。
- 门户价格是最低变体的价格，无论是否有库存，这样当某个尺码售罄时目录不会显示价格变动；库存是总和。门户从定价上下文中读取每个变体的价格范围。
- 标题、描述和图片描述的是产品族。变体可以覆盖它继承的任何字段（某个颜色有自己的图片）。在产品族详情内，每个变体是一行紧凑行：id、选项值、价格、库存，以及仅与产品族不同的字段。
- 只有列出的变体存在。如果 king/blush 行不存在，该产品不销售 king/blush；代理会说明并推荐最接近的已有变体。

**变体数量。**  详情在一个受限结果中返回产品族的所有变体，上限为 `max_fenced_chars`（默认 12,000 个字符）。一行紧凑行约 70 到 120 个字符，因此一个产品族最多容纳约六十个变体。更大的矩阵应按主要选项拆分为多个产品族：一双鞋有八种颜色和十四种尺码，就拆成八个产品族，每个十四个变体。超过上限时结果会被截断且不报错，因此请用你最大的产品族来测试。

**缺货。**  当 `add_to_cart` 指定的变体存在但无法购买时，抛出 `Unavailable`，消息中只包含 id：哪个缺货，以及哪些同族变体有库存。executor 中继该消息，不执行写入。零售和电信示例实现了这一点。对于商店完全不销售的商品，使用 `NotOffered` 和 `enable_*` 开关。

## 第 5 步：将商户写入应用到产品族

| 写入操作 | 指定对象 | 对产品族 id 的影响 |
|---|---|---|
| 价格更新 | 变体 | 由 executor 持有，指向变体 id；"所有尺码涨 5%"对每个变体生成一个条目 |
| 补货 | 变体 | 同上 |
| 暂停或激活 | 均可 | 将所有变体下架或重新上架 |
| 促销 | 均可 | 展开为每个变体一行，每行有自己的调整前后价格；每个变体计入每次变更的条目上限 |
| 内容编辑 | 均可 | 编辑共享内容；如果后端的变体共享产品族的内容字段，则拒绝在变体上编辑这些字段，如零售示例所示 |

如果你的领域使用其他字段名表示价格（每晚价格、费用），请将其添加到商户配置的 `price_bearing_fields` 中，否则价格上限检查不会生效。

## 第 6 步：对平台无法提供的数据返回 `None`

不要返回替代的零值。返回 `None` 并在简短备注中说明原因。

| 位置 | 返回值 |
|---|---|
| 业务快照 | 对缺少的流量、转化率或平均订单值返回 `None`；备注说明缺少哪些 |
| 指标序列 | 返回空序列并附带说明原因的备注 |
| 营销活动 | 对渠道未报告的花费或收入返回 `None` |
| 定价上下文 | `min_price_basis`：底价是基于商品成本还是店铺规则 |
| 库存预警、订单问题 | 当平台没有此类对象时，从库存和订单派生预警和问题；仅返回你能计算的类型 |
| 商户上下文 | 一个 `limitations` 列表（来源和每条一句描述），用于全店范围的数据缺口，如较短的订单历史 |

零售商户示例返回两个限制：90 天的订单历史和一个不报告收入的邮件渠道。

## 在示例中的体现

- 零售目录：按尺码分的床垫（一个尺码缺货，价格递增），按尺码和颜色分的枕套套装（一个组合缺货），六个色号同价的有色保湿霜，以及描述中说明选重规则的加重毯。
- 电信目录：按存储容量和颜色分的手机，每个变体有分期付款。
- 测试数据在产品族下紧凑地编写变体；共享加载器填充其余部分并派生选项。数据结构就是详情工具返回的内容。
- 零售和电信的 `merchant_inventory.json` 持有匹配的变体行；零售商户上下文展示了 `limitations`；娱乐示例展示了固定顺序的流程。
